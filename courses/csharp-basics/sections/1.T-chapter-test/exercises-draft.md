## What this boss is
The **Chapter 1 region boss.** Integrative: it combines everything from 1.1–1.5 (the program & its
variables) into realistic multi-skill scenarios. **No new material** is taught. Passing it **lights the
Chapter 1 region** (Oberösterreich) on the map.

## The skills it integrates (1.1–1.5 only)
- 1.1 program skeleton (explicit `using/class/Main`)
- 1.2 output: `WriteLine`/`Write`, blank lines, escapes (`\n`, `\t`, `\"`, `\\`), exact formatting
- 1.3 numbers: `int`/`double`, choose the type, `const`, combine with `+ - *`
- 1.4 text: `string`/`char`, light `bool`, `const string`
- 1.5 naming: legal + conventional + meaningful names

## Hard scope boundary (same as Ch.1)
- **NO input / NO `ReadLine` / NO parsing**, that's Chapter 2's boss. 1.T problems **author their values
  into the program** (baked-in literals), compute, and print.
- **NO `/`, NO `%`**, arithmetic is `+ - *` only (Ch.3 is arithmetic in depth).
- **NO concatenation/interpolation grading as the *point***, formatting is via `WriteLine`/escapes; a
  problem may use interpolation incidentally but the boss doesn't *require* §2.3's skill.

## Test format (NEW shape, a test is NOT a section; flag for AUTHORING-GUIDE + architecture §5)
A chapter test is **pooled**, so its folder differs from a section:

```
1.T-chapter-test/
  README.md            boss spec + pool index
  exercises-draft.md   this file
  test.yaml            SOURCE OF TRUTH: draw size, light threshold, window, the pool (ordered problem IDs)
  cheatsheets/         the gathered 1.1–1.5 section cheatsheets (the "cheatsheet library", scope scales up)
  pool/
    pNN-slug/          one folder per POOL problem, same shape as a section problem
                       (problem.yaml / design.md / starter.cs / solution.cs ; expecteds via the CLI)
```

- **The pool is bigger than the draw** → non-memorizable. Each attempt draws a fresh set.
- **`test.yaml` (proposed shape):**
  ```yaml
  id: csharp-basics/1.T
  kind: chapter-test
  draw: 10            # how many problems a single attempt serves
  light_at: 6         # ~60% of the draw lights the region
  window_hours: 24    # generous attempt window; miss it → doesn't light, retry gets a fresh draw
  shuffle: true
  pool:               # ordered problem IDs in pool/ (bank the attempt draws from)
    - p01-...
    - ...             # ~20 entries
  ```
- **No per-section `lights_at`/count here**, the test's completion is `draw` + `light_at`, not a problem
  count. (Backend enforces, reads these from the manifest, consistent with §5.)

## Size (decided)
- **Pool ≈ 20 problems.** **Draw = 10.** **Light at 6** (~60% of the draw). ~24h window, fresh draw on retry,
  no lockouts.
- The boss costs more to author than a section (≈20 integrative problems), that's expected; it's the
  region boss.

## Anti-hardcoding (decided), the POOL is the defense
No stdin here, so the usual "varied inputs per case" doesn't apply. Instead:
- **The pool holds many VALUE-VARIED VARIANTS.** Each scenario family exists as several pool entries with
  **different baked-in literals** (different field values, different constants, different target numbers).
- Memorizing one attempt's outputs **fails on the next draw** (different variant, different expected).
- Each pool problem still gets its (deterministic, no-stdin) expected generated by the **oracle CLI** from
  its `solution.cs`, the human never types the answer, exactly as for sections.
- **Difficulty weighting:** pool skews ●●/●●● (integrative), with a few ● warm-ups so the draw isn't a wall.

## Statement style
- Terse (course-wide). For formatted-output bosses, prefer *"Print exactly this:"* + the target block.
- Capstone-ish problems may use a few more words of scenario setup, only as needed.

## The pool (≈20), organized by scenario family

> Each family appears as **multiple value-varied variants** (that's the anti-hardcoding). The table lists
> families + how many variants; the per-family intent follows.

| Family | Variants | What it integrates | Diff |
|--------|----------|--------------------|------|
| A, declare the fields | 4 | types + naming + multi-line formatted output | ●● |
| B, named constants | 4 | `const` + `+ - *` + output (magic-numbers → named) | ●● |
| C, model & format | 5 | choose types + compute `+ - *` + exact formatted block | ●●● |
| D, fix the broken integrative program | 4 | debug across skeleton/type/naming/output | ●● |
| E, reproduce the exact report | 3 | pure precision: escapes + layout to spec | ●●●→● mix |

*(4 + 4 + 5 + 4 + 3 = 20. A draw of 10 pulls a mix across families + difficulties.)*

## Per-family intent (the bones)

### A, "declare the fields" (×4 variants)
Given a described **thing** (variant it: a book / a product / a student record / a city entry), declare its
typed, well-named fields (`string`, `int`, maybe `double`/`char`/`const`), and print a tidy **multi-line
block** to spec. Integrates 1.3 + 1.4 + 1.5 + 1.2 formatting. Variants change the thing + the field values.

### B, "named constants" (×4 variants)
Given a snippet full of **magic numbers**, replace them with well-named `const`s and print the computed
result (compute with `+ - *`). Integrates 1.3 (`const`, arithmetic) + 1.5 (naming) + 1.2 (output). Variants
change the constants + the computation (area, total price = count*unit, a week→days figure, etc.).

### C, "model & format" (×5 variants), the heaviest
A short scenario: choose the right types, declare well-named variables (incl. a `const`), compute a value
with `+ - *`, and print an **exactly-formatted** block (escapes/tabs/blank lines). The fullest integration
of the chapter. Variants change the scenario + numbers + the required layout.

### D, "fix the broken integrative program" (×4 variants), the debug boss
Given a multi-skill program with a **planted bug**, fix it so it compiles and prints the target. Bug varies
per variant across the chapter's signature mistakes: a broken skeleton (missing `;`/brace, 1.1), a wrong
type (`int` where fractional needed, 1.3), a quoting bug (`"A"` vs `'A'`, 1.4), an assignment-order bug
(1.3), an illegal name that won't compile (1.5). Proves *reading & repairing* integrated code.

### E, "reproduce the exact report" (×3 variants), the precision boss
*"Print exactly this:"* + a small fixed formatted report (a bordered box of fields, an aligned 2-column
mini-table, a receipt-style block). Pure 1.2 precision at boss scale, strict byte-match, tabs-not-spaces,
exact blank lines. Variants change the report content/shape. Keep each tiny + fixed.

# 5.T, Chapter 5 Test (region boss)

The Chapter 5 region boss. It combines everything from 5.1 to 5.5 (resting on Chapters 1 to 4) into realistic
repetition scenarios. No new material is taught. Passing it lights the Chapter 5 region on the map.

## How it works
- **Pooled:** a single attempt draws **10** problems from the **20**-problem pool below. Passing **6** lights
  the region (~60%). A generous **24h** window; miss it or fall short and it simply does not light, a retry
  draws a fresh set. No lockouts, ever.
- **Non-memorizable, from both sides:** the pool is bigger than the draw, AND each pool problem takes stdin,
  so it carries several input cases that vary the iteration count. Memorizing one attempt's answers does not
  survive the next draw, and an unrolled or fixed-output answer cannot pass a problem's own varied cases.
- Source of truth: `test.yaml`. Each pool problem is an ordinary problem folder under `pool/`; expecteds are
  generated by the oracle CLI from each `solution.cs`.

## Scope (same boundary as Chapter 5)
- **Input is used:** values come in via stdin. Prompts are printed on their own line, and the prompt text is
  part of the graded output.
- **The full loop toolkit from this chapter:** `while` (5.1), `do-while` (5.2), `for` (5.3), nested loops
  (5.4), and `break`/`continue` (5.5), on top of types, input, parsing, arithmetic, and the decision toolkit
  from Chapters 1 to 4. The count pattern (read `n`, process `n` values) and the sentinel pattern (read until
  a stop value) are both in play.
- **No methods, no arrays** (Chapters 6 and 7). Accumulate into a single variable; build shapes with nested
  loops; steer with `break`/`continue`.

## Anti-hardcoding: vary the iteration count
This is the loops boss, so the per-problem rule is the Chapter 5 one: each problem's cases **vary the number
of iterations**, zero / one / several, with a **zero-iteration case wherever the loop can run zero times**.
Nested problems vary both bounds (including a 1-by-k edge); control problems cover the first/late/never and
none/some/all paths. A loop is deterministic per stdin, so the oracle `gen`/`check` work unchanged. **Every
solution terminates; no committed input loops forever, and any `while (true)` has a reachable `break`.**
